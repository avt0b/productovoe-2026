# mobile — AR-модуль «Маршруты победы»

Android-проект с одним модулем `:ar`. Это **библиотека**, а не приложение:
её подключает к себе клиент платформы, каким бы он ни был.

## Главное решение: ARCore здесь не нужен

Макет AR-экрана состоит из:

- живого кадра камеры на весь экран;
- метки цели в конкретной точке кадра («След кабельного окопа · 18 м»);
- строки компаса `AZ 048° СВ` / `ELEV +4.2°`;
- персонажа-проводника, **приклеенного к нижней трети экрана** (в макете это
  плоская картинка с размытой тенью-подложкой, а не объект на земле);
- субтитров, полосы прогресса и кнопок.

Ни одного элемента, который требовал бы обнаружения плоскостей, якорей или
SLAM. Значит, ARCore не нужен, а вместе с ним не нужны Sceneform (архивирован),
SceneView и Filament. Достаточно: **CameraX + датчик ориентации + GPS +
overlay на Compose**.

Это не упрощение ради скорости, а следствие макета. Практические последствия:

- работает на любом Android без Google Play Services for AR;
- нет зависимости от списка ARCore-совместимых устройств;
- экран запускается за доли секунды вместо инициализации трекинга;
- всё, что считается, — чистая математика, а её можно покрыть обычными тестами.

Если позже захочется, чтобы проводник действительно стоял на земле и оставался
на месте при обходе вокруг, — это отдельная задача поверх готового модуля,
а не переписывание.

        │   │   ├── Geo.kt        расстояние, азимут, склонение, угол места

        │   │   ├── OrientationFilter.kt  сглаживание компаса
        │   │   └── ArScene.kt    сборка состояния экрана
        │   ├── ui/               Compose: экран, HUD, метка, проводник
        │   │   ├── ArTheme.kt    токены макета один в один

### Экран

`ArScreen` принимает готовое `ArSceneState` и ничего не вычисляет сам —
вся геометрия посчитана в домене и покрыта тестами.

Кадр камеры приходит **слотом** `cameraFeed`. В бою туда кладётся `PreviewView`
от CameraX, в превью и на показе — статичная картинка. Из-за этого весь экран
рисуется в Android Studio без телефона, а на защите работает без окна и неба.

Ассет проводника — тоже слот. Модуль не тащит картинку внутрь себя, поэтому
собирается и открывается до того, как персонаж нарисован.

### Почему домен отделён от Android

`domain` не импортирует ни одного класса из `android.*`. Поэтому вся
математика наведения проверяется обычным `junit` за секунды, без эмулятора и
телефона. Именно там живут настоящие ошибки: переход компаса через 0°, знак
склонения, поведение при плохом GPS.

## Контракт модуля

Хост собирает `ArPointSpec` и получает `ArResult`. Модуль не знает ни о
навигации приложения, ни о его сети.

```kotlin
ArPointSpec(
    pointId = "wp-2",
    title = "Рубеж связистов",
    stepIndex = 2, stepTotal = 4,
    target = ArTarget(GeoPoint(52.9706, 36.0672), label = "След кабельного окопа"),
    companion = CompanionSpec(name = "Санитарный пёс Верный", ...),
    narration = NarrationSpec(audioUri = ..., subtitles = ...),
)
```

Важная деталь: `companion` **обнуляемый**. `null` означает, что проводника на
этой точке быть не должно. Это не косметика — мультяшный маскот у братской
могилы читается как неуважение, поэтому решение принимает бэкенд (флаг у типа
точки), а модуль его исполняет.

`ArResult.Unavailable` возвращается, когда нет разрешения на камеру или нет
датчика ориентации. Хост в этом случае показывает обычную карточку точки:
AR никогда не должен становиться единственным способом пройти маршрут.

## Как тестировать

Четыре уровня, от дешёвого к дорогому.

### 1. JVM-тесты домена — основная страховка

```bash
gradlew :ar:testDebugUnitTest
```

Секунды, без устройства. Сейчас **51 тест**: гео-математика, проекция в кадр,
фильтр компаса, сборка состояния сцены, выбор субтитра по таймкоду, румбы,
формат координат. Значения сверены с независимой реализацией формул.

### 2. Compose-превью — UI без запуска

Шесть готовых превью в `ArPreviews.kt`. Это не витрина, а инструмент: каждое
состояние трудно или невозможно поймать руками на устройстве.

| Превью | Что проверяет |
| --- | --- |
| Цель в кадре | метка встала по центру, идёт рассказ |
| Цель за кадром слева | подсказка «поверните левее» с дистанцией |
| Плохой GPS | метка спрятана, показана причина |
| Находка подтверждена | всплывающая плашка |
| Мемориал — без проводника | экран цел без маскота (этическое правило) |
| Камера недоступна | вместо чёрного экрана — объяснение |

Открывается в панели Preview Android Studio. Ни камеры, ни телефона.

### 3. Эмулятор — сценарий подхода к точке

Нужен системный образ (сейчас в SDK его нет — ставится через
SDK Manager → System Images).

Что даёт эмулятор:

- **Extended controls → Location** — можно загрузить GPX-трек и проиграть
  маршрут: приложение увидит, как пользователь подходит к точке;
- **Extended controls → Virtual sensors** — вручную поворачивать устройство
  и проверять, что метка ходит по кадру правильно;
- виртуальная сцена вместо камеры.

Этого хватает, чтобы отладить весь сценарий «подошёл — повернулся — нашёл»,
не выходя на улицу.

### 4. Живое устройство — то, что эмулятор не покажет

Реальный шум датчиков и реальная погрешность GPS. `adb` уже есть в SDK:

```bash
adb install -r ar-demo.apk
```

Проверять надо именно дрожание метки и поведение компаса рядом с металлом —
на эмуляторе этого не бывает.

### Режим симуляции для защиты

Отдельно от тестов: источники камеры, ориентации и гео скрыты за интерфейсами,
и есть их подставные реализации со сценарием. Это нужно **для демонстрации**:
в зале нет ни неба, ни ориентиров, ни нормального GPS, а показывать AR
как-то надо. Симуляция проигрывает записанный трек поверх статичного кадра.

## Известные подводные камни

- **Магнитное склонение.** Датчик даёт азимут от магнитного севера, а
  `bearingDegrees` считает от истинного. В Орловской области расхождение около
  +9° — без поправки метка уезжает почти на треть ширины кадра. Поправка берётся
  из `android.hardware.GeomagneticField`, функция `applyDeclination` уже есть.
- **Дрожание компаса.** Сырой азимут скачет на несколько градусов даже в покое.
  Без `OrientationFilter` метка вибрирует и выглядит как баг.
- **Точность GPS.** При разбросе больше 40 м наведение бессмысленно: модуль
  прячет метку и говорит об этом прямо, вместо того чтобы показывать
  правдоподобную ложь.
- **Яркое солнце.** Персонаж без контурной обводки и тени сливается с фоном.

## Сборка

JDK берётся из Android Studio (`<студия>/jbr`), SDK — из `local.properties`
(файл в git не попадает).

```bash
gradlew :ar:testDebugUnitTest   # тесты домена
gradlew :ar:assembleDebug       # сборка библиотеки
```

Версии зафиксированы в `gradle/libs.versions.toml`: AGP 9.3.2, Gradle 9.5.0,
compileSdk 37, minSdk 26.

> AGP 9 несёт поддержку Kotlin внутри себя — отдельный плагин
> `org.jetbrains.kotlin.android` подключать **нельзя**, он конфликтует за
> расширение `kotlin`.


## Что сделано и что дальше

Готово и собирается (`:ar:assembleDebug` даёт AAR):

- контракт модуля и домен наведения — 51 тест;
- экран на Compose по макету: HUD, компас, метка цели, подсказка поворота,
  проводник, панель реплики, плашки состояний;
- шесть превью и записанный сценарий симуляции.

Не сделано — это Android-обвязка, следующий шаг:

1. **CameraX** — реальный кадр в слот `cameraFeed`, запрос разрешения,
   получение угла обзора камеры вместо значения по умолчанию.
2. **Датчики** — `TYPE_ROTATION_VECTOR` → азимут и наклон, поправка на
   склонение через `GeomagneticField`, прогон через `OrientationFilter`.
3. **Геолокация** — `FusedLocationProviderClient`, точность в `LocationFix`.
4. **Звук** — `MediaPlayer`/`ExoPlayer` и синхронизация позиции с субтитрами.
5. **`ArActivity`** — сборка всего вместе и `ActivityResultContract`,
   чтобы хост запускал экран одним вызовом и получал `ArResult`.
6. **Ассет проводника** — спрайт или короткое видео с альфа-каналом.
