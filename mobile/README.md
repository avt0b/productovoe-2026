# mobile — AR-модуль «Маршруты победы»

Android-проект с одним модулем `:ar`. Это **библиотека**, а не приложение:
её подключает к себе клиент платформы, каким бы он ни был.

## Два режима экрана

**Компасный — без ARCore.** Кадр CameraX, датчик ориентации, GPS и overlay на
Compose. Метка цели стоит в той точке кадра, куда смотрит камера, проводник —
плоская фигура в нижней трети экрана. Работает на любом Android без Google Play
Services for AR и стартует за доли секунды. Вся математика — чистые функции
под тестами.

**С маркером — ARCore.** Если у точки есть табличка (`MarkerSpec`), экран
поднимает сессию ARCore, находит картинку в кадре и ставит 3D-проводника прямо
на неё. Компас и GPS здесь не помогают: их ошибка — десятки метров и градусов,
персонаж на них плавал бы по кадру. Табличка даёт позу с точностью до
сантиметров, а дальше мир держит сам ARCore: отвёл камеру — проводник стоит
где стоял.

Сначала ARCore был не нужен: макет рисовал проводника плоской картинкой,
приклеенной к экрану. Требование «персонаж стоит на конкретном месте» это
решение поменяло, но компасный режим остался. Нет ARCore на телефоне, нет
таблички у точки или сессия не поднялась — экран возвращается к нему сам.

### Экран

`ArScreen` принимает готовое `ArSceneState` и ничего не вычисляет сам —
вся геометрия посчитана в домене и покрыта тестами.

Кадр камеры приходит **слотом** `cameraFeed`. В бою туда кладётся `PreviewView`
от CameraX, в превью и на показе — статичная картинка. Из-за этого весь экран
рисуется в Android Studio без телефона, а на защите работает без окна и неба.

Ассет проводника — тоже слот. Модуль не тащит картинку внутрь себя, поэтому
собирается и открывается до того, как персонаж нарисован.

### Почему домен отделён от Android

`domain` не импортирует ни одного класса из `android.*`. Поэтому вся
математика наведения проверяется обычным `junit` за секунды, без эмулятора и
телефона. Именно там живут настоящие ошибки: переход компаса через 0°, знак
склонения, поведение при плохом GPS.

## Контракт модуля

Хост собирает `ArPointSpec` и получает `ArResult`. Модуль не знает ни о
навигации приложения, ни о его сети.

```kotlin
ArPointSpec(
    pointId = "wp-2",
    title = "Рубеж связистов",
    stepIndex = 2, stepTotal = 4,
    target = ArTarget(GeoPoint(52.9706, 36.0672), label = "След кабельного окопа"),
    companion = CompanionSpec(name = "Санитарный пёс Верный", ...),
    narration = NarrationSpec(audioUri = ..., subtitles = ...),
    marker = MarkerSpec(
        assetPath = "markers/wp-2.png",
        physicalWidthMeters = 0.30f,          // ширина таблички; null — ARCore измерит сам
        fallbackInFrontAfterMillis = 4_000,   // не нашли — встать перед камерой
    ),
)
```

`marker` тоже обнуляемый: без таблички экран работает в компасном режиме.

Важная деталь: `companion` **обнуляемый**. `null` означает, что проводника на
этой точке быть не должно. Это не косметика — мультяшный маскот у братской
могилы читается как неуважение, поэтому решение принимает бэкенд (флаг у типа
точки), а модуль его исполняет.

`ArResult.Unavailable` возвращается, когда нет разрешения на камеру или нет
датчика ориентации. Хост в этом случае показывает обычную карточку точки:
AR никогда не должен становиться единственным способом пройти маршрут.

## Как тестировать

Четыре уровня, от дешёвого к дорогому.

### 1. JVM-тесты домена — основная страховка

```bash
gradlew :ar:testDebugUnitTest
```

Секунды, без устройства. Сейчас **112 тестов**: гео-математика, проекция в кадр,
фильтр компаса, сборка состояния сцены, углы обзора и поправка на кадрирование,
выбор субтитра по таймкоду, румбы, формат координат, место проводника у
таблички, сальто, соглашения SceneView о поворотах. Значения сверены
с независимой реализацией формул.

### 2. Compose-превью — UI без запуска

Шесть готовых превью в `ArPreviews.kt`. Это не витрина, а инструмент: каждое
состояние трудно или невозможно поймать руками на устройстве.

| Превью | Что проверяет |
| --- | --- |
| Цель в кадре | метка встала по центру, идёт рассказ |
| Цель за кадром слева | подсказка «поверните левее» с дистанцией |
| Плохой GPS | метка спрятана, показана причина |
| Находка подтверждена | всплывающая плашка |
| Мемориал — без проводника | экран цел без маскота (этическое правило) |
| Камера недоступна | вместо чёрного экрана — объяснение |

Открывается в панели Preview Android Studio. Ни камеры, ни телефона.

### 3. Эмулятор — сценарий подхода к точке

Нужен системный образ (сейчас в SDK его нет — ставится через
SDK Manager → System Images).

Что даёт эмулятор:

- **Extended controls → Location** — можно загрузить GPX-трек и проиграть
  маршрут: приложение увидит, как пользователь подходит к точке;
- **Extended controls → Virtual sensors** — вручную поворачивать устройство
  и проверять, что метка ходит по кадру правильно;
- виртуальная сцена вместо камеры.

Этого хватает, чтобы отладить весь сценарий «подошёл — повернулся — нашёл»,
не выходя на улицу.

### 4. Живое устройство — то, что не покажет ничто другое

Реальный шум датчиков, реальная погрешность GPS, реальное поведение компаса
рядом с арматурой. Для этого в проекте есть модуль `:demo` — тонкая обёртка,
которая ставится на телефон и запускает AR-экран с произвольной целью.

**Подготовка телефона.** Настройки → «О телефоне» → семь раз по «Номер сборки»,
затем «Для разработчиков» → «Отладка по USB».

**Установка:**

```bash
gradlew :demo:installDebug
```

**Разрешения — сразу, без тапов по диалогам:**

```bash
adb shell pm grant ru.marshruty.ardemo android.permission.CAMERA
adb shell pm grant ru.marshruty.ardemo android.permission.ACCESS_FINE_LOCATION
```

**Беспроводная отладка — не роскошь.** Проверять наведение надо на улице, а с
кабелем туда не выйдешь. На Android 11+: «Для разработчиков» → «Беспроводная
отладка» → «Подключить устройство с помощью кода».

```bash
adb pair 192.168.1.50:41234
adb connect 192.168.1.50:37000
```

После этого телефон отвязывается от компьютера, а `logcat` продолжает идти.

#### Процедура проверки — минут десять

**Шаг 1. Компас.** Открыть AR, посмотреть на строку сверху: `AZ 048° СВ`,
`GPS ±8 м`, `ELEV +2.1°`.

Повернуться на север по любому компасу — `AZ` должен показать около `000° С`.
На восток — около `090° В`. Не сходится: отойти от металла и поводить телефоном
«восьмёркой», магнитометр перекалибруется.

**Шаг 2. Знак наклона — проверить обязательно.**

Навести камеру на горизонт: `ELEV` около `0.0°`. Поднять камеру к потолку:
`ELEV` должен **расти** — до `+30`, `+60`.

Если вместо этого он уходит в минус, в `SensorOrientationSource` надо убрать
минус перед `Math.toDegrees(angles[1])`. Правка на один символ, но без неё
метка по вертикали уезжает в противоположную сторону. Знак зависит от того,
как конкретная прошивка отдаёт пересчитанные оси, поэтому выбрать его заранее
нельзя — только проверить на живом устройстве.

**Шаг 3. Наведение на местности.**

1. Выйти на открытое место, дождаться в HUD `GPS ±10 м` или лучше.
2. На стенде нажать «Взять мои текущие координаты».
3. Отойти на 30–40 шагов в любую сторону.
4. Открыть AR и повернуться туда, откуда пришли.

Метка обязана стоять там, где вы стояли, а расстояние — совпадать с пройденным.
Это единственная проверка, которая ловит всю цепочку разом: гео, компас,
склонение, углы обзора, проекцию.

#### Что означают отклонения

| Симптом | Причина | Куда смотреть |
| --- | --- | --- |
| Метка стабильно смещена вбок примерно на 10° | знак магнитного склонения | `applyDeclination` в `Geo.kt` |
| Смещение тем больше, чем ближе к краю кадра | неверный угол обзора | `croppedFieldOfView`, `FRAME_ASPECT_RATIO` в `ArHost` |
| Метка дрожит в покое | мало сглаживания | `smoothing` у `OrientationFilter` |
| Метка отстаёт при повороте | много сглаживания | там же, в другую сторону |
| По вертикали уезжает наоборот | знак наклона | шаг 2 |
| «СИГНАЛ GPS СЛАБЫЙ» на открытом месте | спутники не пойманы | подождать 30–60 секунд |

#### Отрицательные сценарии — про них забывают

- Отозвать разрешение камеры в настройках и открыть AR: экран должен закрыться
  с `Unavailable`, а хост — показать обычную карточку точки. Чёрный экран
  вместо этого означает, что хост не обрабатывает результат.
- Зайти в помещение: точность падает за 40 м, метка обязана **исчезнуть**,
  а вместо неё появиться плашка «СИГНАЛ GPS СЛАБЫЙ».
- Открыть на стенде «точку без проводника»: пёс не появляется, экран остаётся
  цельным. Это проверка этического правила, а не косметики.

#### Режим с маркером

На стенде — «Открыть AR с маркером». Маркер точки лежит в
`ar/src/main/assets/markers/wp-2.png`: распечатать на A4 горизонтально шириной
около 30 см или открыть во весь экран ноутбука.

1. **Поиск.** Сверху плашка «ИЩУ ТАБЛИЧКУ». Навести камеру на картинку —
   плашка пропадает, проводник встаёт на неё.
2. **Мир держится.** Отвести камеру от картинки и вернуть: проводник стоит на
   том же месте, а не пропадает и не прыгает.
3. **Лицом к человеку.** Обойти картинку сбоку — проводник поворачивается к
   камере. Сбоку видна спина — сломан знак поворота, см. `SceneViewConventionTest`.
4. **Сальто.** Кнопка «Сальто»: присед, оборот назад, приземление на ноги.
5. **Без таблички.** Навести камеру в сторону и подождать 4 секунды — проводник
   встанет в 80 см перед камерой. Показать табличку — перейдёт на неё.

| Симптом | Причина |
| --- | --- |
| «ИЩУ ТАБЛИЧКУ» не пропадает | блики на экране, картинка мелкая в кадре, мало света |
| Проводник заметно больше или меньше таблички | ширина в `MarkerSpec` не совпадает с настоящей — укажите верную или `null` |
| «ТЕРЯЮ ОКРУЖЕНИЕ» | резкое движение или однородная стена в кадре |
| «МАРКЕР НЕ ПОДХОДИТ» | мало деталей на картинке: однотонные поля, повторяющийся узор |
| Проводник кривой, не того роста, висит в воздухе | модель не прошла через `normalize_companion.py` |

```bash
adb logcat -s ArCameraPreview:V CameraOpticsSource:V ArMarkerScene:D AndroidRuntime:E
```

### Режим симуляции для защиты

Отдельно от тестов: источники камеры, ориентации и гео скрыты за интерфейсами,
и есть их подставные реализации со сценарием. Это нужно **для демонстрации**:
в зале нет ни неба, ни ориентиров, ни нормального GPS, а показывать AR
как-то надо. Симуляция проигрывает записанный трек поверх статичного кадра.

## 3D-проводник и маркеры

### Модель

Формат — `.glb` (glTF 2.0 одним файлом). Перед тем как класть модель в
`assets`, её надо нормализовать:

```bash
python tools/normalize_companion.py raw/dog.glb ar/src/main/assets/companion/dog.glb
```

Скрипт считает габариты так, как модель нарисует GPU — со скиннингом, — и
добавляет корневую ноду: рост 1.0, ноги на нуле, центр по X и Z в нуле. Рост
в метрах потом задаётся одним множителем, `MarkerSpec.companionHeightMeters`.

Почему не `scaleToUnits` в рантайме: Filament меряет модель по иерархии нод без
скиннинга, а у моделей со скелетом это другая поза. У тестового Шрека габариты
без скиннинга 364×275×115 с центром на высоте 137, а нарисованный персонаж —
110×83×35 с ногами на нуле. Масштаб по неверной коробке и дал кривую модель.

Ещё скрипт переводит материалы `BLEND` в `OPAQUE` — экспорт из Blender часто
делает полупрозрачным всё тело — и выкидывает ноды по имени (`--drop`).

Модель должна смотреть лицом на +Z. Анимации внутри не обязательны: сальто и
дыхание сделаны трансформацией узлов.

### Маркер

```bash
python -m pip install pillow qrcode
python tools/make_marker.py --point-id wp-2 --title "Рубеж связистов" \
    --step "Точка 2 из 4" --out ar/src/main/assets/markers/wp-2.png
```

ARCore узнаёт картинку по углам и перепадам яркости, поэтому маркер —
неповторяющаяся мозаика в цветах кейса. Голый QR-код подходит плохо: у него
повторяющаяся сетка. QR в углу — ссылка на точку для тех, у кого нет AR.

Ширина картинки задаётся в `MarkerSpec.physicalWidthMeters`. Для напечатанной
таблички на точке её стоит указать — поза точная с первого кадра. Для показа на
экранах разного размера — оставить `null`: ARCore измерит ширину сам за пару
секунд движения камеры, а рост проводника посчитается от измеренной. Неверная
ширина хуже отсутствующей: маркер на телефоне шириной 6 см при заявленных 30 см
дал проводника впятеро больше таблички и в стороне от неё.

### Лицензии

Шрек со Sketchfab — временная затычка для проверки. В репозиторий он не
попадает (`.gitignore`), на защите его быть не должно.

## Известные подводные камни

- **Магнитное склонение.** Датчик даёт азимут от магнитного севера, а
  `bearingDegrees` считает от истинного. В Орловской области расхождение около
  +9° — без поправки метка уезжает почти на треть ширины кадра. Поправка берётся
  из `android.hardware.GeomagneticField`, функция `applyDeclination` уже есть.
- **Дрожание компаса.** Сырой азимут скачет на несколько градусов даже в покое.
  Без `OrientationFilter` метка вибрирует и выглядит как баг.
- **Точность GPS.** При разбросе больше 40 м наведение бессмысленно: модуль
  прячет метку и говорит об этом прямо, вместо того чтобы показывать
  правдоподобную ложь.
- **Яркое солнце.** Персонаж без контурной обводки и тени сливается с фоном.
- **Камеру держит кто-то один.** ARCore и CameraX не откроют её одновременно,
  поэтому в каждый момент работает один режим экрана.
- **Долгий подъём ARCore.** Движок, материалы SceneView, сессия и камера
  поднимаются на главном потоке около двух секунд, и ускорить это снаружи
  нельзя. Поэтому AR-экран сначала рисуется с подписью «Запускаю AR-камеру»,
  а сцена создаётся кадром позже — иначе все две секунды висит замёрзшая
  кнопка предыдущего экрана.
- **ARCore и главный поток.** `AugmentedImageDatabase.addImage` переводит
  картинку в оттенки серого попиксельно. На маркере 1600×1100 это держало
  главный поток 2.5 секунды. База собирается в фоне, картинка перед этим
  уменьшается до 800 px.
- **Перерисовка каждый кадр.** Часы экрана читаются только через
  `derivedStateOf`, а поза 3D-проводника пишется кадровым колбэком узла.
  Иначе экран на 120 Гц перерисовывался бы 120 раз в секунду ради субтитров,
  которые меняются раз в несколько секунд.

## Сборка

JDK берётся из Android Studio (`<студия>/jbr`), SDK — из `local.properties`
(файл в git не попадает).

```bash
gradlew :ar:testDebugUnitTest   # тесты
gradlew :demo:installDebug      # стенд на подключённый телефон
```

Версии зафиксированы в `gradle/libs.versions.toml`: AGP 9.3.2, Gradle 9.7.1,
Kotlin 2.4.10, SceneView 4.34.0, compileSdk 37, minSdk 26.

> **Kotlin 2.4.10**, а не встроенный в AGP 9.3.2 2.2.10: ARSceneView собран
> Kotlin 2.4.10, и компилятор младше его метаданные не читает. Версию поднимает
> объявление `org.jetbrains.kotlin.android` в корневом `plugins { … apply false }`.
> В сами модули этот плагин подключать **нельзя**: AGP 9 несёт поддержку Kotlin
> внутри себя, и плагин конфликтует за расширение `kotlin`.

> **Filament отдельно не подключать.** SceneView везёт свой, и его материалы
> собраны под эту версию движка. Более новый Filament поднимет версию и уронит
> загрузку материалов на старте.

> Интернет через локальный прокси (VPN-клиент) Gradle сам не увидит: JVM не
> читает `HTTPS_PROXY`. Прописать в `~/.gradle/gradle.properties`, а не в
> проектный файл — адрес прокси у каждого свой:
> `systemProp.https.proxyHost=127.0.0.1` и `systemProp.https.proxyPort=<порт>`.

## Что сделано и что дальше

Готово, собирается и проверено на Xiaomi 13 Lite:

- контракт модуля и домен — 112 тестов на JVM;
- компасный режим: CameraX, датчик вращения с поправкой на склонение, GPS,
  метка цели, подсказки поворота, плашки состояний;
- режим с маркером: ARCore, трекинг картинки, 3D-проводник на табличке,
  поворот к человеку, сглаживание позы, запасное место перед камерой;
- сальто трансформацией — одинаково для 3D и для плоского персонажа;
- угол обзора в режиме маркера — из параметров камеры ARCore, а не под CameraX;
- производительность: маркер разбирается в фоне, модель грузится асинхронно,
  экран не перерисовывается каждый кадр;
- инструменты: нормализация модели и генерация маркеров.

Дальше:

   цель в 800 м выглядит так же, как в 20 м.
3. **Засчитывание точки.** Тап по метке сразу возвращает `Completed`, без
   проверки, что человек рядом.
4. **Настоящий проводник.** Модель пса вместо Шрека, через `normalize_companion.py`.
