# План доработок мобильного клиента: восемь задач на две сессии

Ветка-основа — `feat/up-mobile` (`ee68c35`). Работают две независимые сессии
Claude на **разных машинах**: сторона A и сторона B. Правило прежнее и жёсткое —
**у каждого файла ровно один владелец**, пересечений по файлам быть не должно
(подробно — [PARALLEL.md](PARALLEL.md), дизайн — [DESIGN.md](DESIGN.md)).

Бэкенд не трогаем: код сервисов правит другая команда, недостающее пишем в
`BACKEND-GAPS.md` (каждая сторона — в свой отчёт, сведёт пользователь).

## 1. Что делаем — восемь задач в понятной формулировке

| № | Как было сказано | Что делаем на самом деле | Сторона |

| 3 | «раздвоение ролей при отправке заявок» | Убрать ситуацию, когда человек висит в двух очередях на роль и молча теряет текущую роль при одобрении; если роли фактически две — дать выбор активной | B |

## 3. Сторона A — задачи по порядку

Порядок не случайный: 5 и 7 — короткие, 6 нужен стороне B, 2 — самая большая.

### A-1. Бамп: радиус 500 м (задача 5)

**Где.** `docker-compose.yml`, блок `search_hq_service`; `.env.example`.

**Что.** Радиус живёт в `backend/search_hq_service/core/config.py`
(`excursion_site_radius_m = 150.0`) и переопределяется переменной окружения —
**код сервиса не правим**:

```yaml
    environment:
      ...
      EXCURSION_SITE_RADIUS_M: ${EXCURSION_SITE_RADIUS_M:-500}
```

В `.env.example` — строка с пояснением, зачем 500 (место сбора у школы, а
группа стоит у автобуса через квартал; погрешность GPS в поле — десятки метров).
Запас на погрешность `BUMP_ACCURACY_SLACK_M` остаётся 50 м, его не трогаем.

**Проверка.** Поднять стенд, открыть сбор в 300 м от точки экскурсии —
раньше «Вы в 300 м от места сбора, подойдите ближе», теперь сбор открывается.
Текстов «150 м» в клиенте нет: цифру в ошибке пишет сервис — убедиться, что в
сообщении теперь 500.

Если правка compose тоже под запретом — не делаем, а пишем в отчёт одну строку
для пользователя: `EXCURSION_SITE_RADIUS_M=500`.

### A-2. Кнопки на экране «Сбор группы» (задача 7)

**Где.** `src/modules/excursions/GatheringPage.vue` (+ при необходимости
`components/` того же модуля).

**Что не так сейчас.**
- «Повести к точке 1: {название}» — длинное название режется `truncate`, из
  кнопки не понять, куда поведём.
- «Начать с другого места» — голый текст без вида кнопки, читается как подпись.
- «Закрыть сбор» — красная текстовая кнопка слева, а подтверждение — самодельная
  пара кнопок, из-за которой блок скачет по высоте.
- Главные действия лежат под списком отметившихся: чем больше группа, тем
  дальше до кнопки.

**Что делаем.**
1. Главное действие — заполненная кнопка в две строки: «Повести группу» и под
   ней место назначения мелким, без `truncate`, с переносом.
2. «Начать с другого места» — вторичная кнопка (контур), не текст.
3. «Закрыть сбор» — деструктивное действие внизу блока через готовый
   `ui/ConfirmAction.vue`, а не своя пара кнопок.
4. Кнопка подготовки («Приготовиться» / «Я на месте — открыть сбор»):
   состояния «ждём GPS», «открываем» со спиннером, заблокирована — с причиной
   рядом, а не молча.
5. Действия краеведа закрепить внизу экрана (sticky), список отметившихся
   прокручивается под ними.
6. Все нажимаемые элементы — не меньше 48 px по высоте, размеры и цвета
   токенами из DESIGN.md (красный — только на действительно деструктивном).

**Проверка.** 375×812 и 375×667; экскурсия с точкой с длинным названием; роли
краеведа и участника; состояния «сбор не открыт», «сбор идёт», «сбор закрыт»,
«никто не отметился».

### A-3. Карта разворачивается по нажатию (задача 6)

**Где.** `src/ui/geo/GeoMap.vue` (+ `src/style.css` при необходимости).

**Что делаем.**
1. Новый проп `expandable?: boolean` (по умолчанию `false`) — **только
   добавляем**, ничего в API компонента не переименовываем и не удаляем: на нём
   стоят экраны обеих сторон.
2. В свёрнутом виде карта — превью: перетаскивание и зум колесом выключены,
   страница прокручивается пальцем поверх карты, нажатие разворачивает.
3. Развёрнутый вид — поверх всего (`Teleport` в `body`), с учётом безопасных
   зон, кнопкой «свернуть» и закрытием по аппаратной кнопке «назад» и Esc.
4. Не ломаем режим выбора точки: где карта эмитит `pick` (выбор места), тап
   по-прежнему ставит точку — эти экраны просто не включают `expandable`.
5. Состояние `selected`, метки, линии и круги сохраняются при разворачивании и
   сворачивании; Leaflet переинициализировать не нужно — достаточно
   `invalidateSize()` после смены размера.

**Проверка.** Свои экраны: список маршрутов, экскурсии. Сторона B включит проп
у себя сама — в отчёте написать, что проп появился и как называется.

### A-4. Обучалка (задача 2)

**Где.** Новый модуль `src/modules/onboarding/` — папку приложение подхватит
само (`src/app/registry.ts` собирает `src/modules/*/index.ts`).

**Что делаем.**
1. Роут `onboarding` (имя фиксировано — на него сошлётся сторона B из
   профиля), **без новой вкладки в нижней панели**: их пять и панель заполнена.
2. Первый запуск после входа — короткое обучение на 4–6 экранов: пять вкладок и
   зачем каждая, роли (семья / поисковик / краевед) и что они дают, первое
   действие («выберите маршрут рядом»). Пропустить можно с любого шага.
3. «Шпаргалка по разделам» — тот же экран, открытый заново: карточки по
   разделам с иконками и одной фразой «что здесь делают», без воды.
4. Текст зависит от роли человека (`session.user.role`) и от семейного и
   детского режима (`usePreferencesStore().familyMode` — **читаем, не правим**).
5. Пройдено или пропущено — свой ключ в `localStorage`
   (`marshruty.client.onboarding`) c номером версии обучения: обновили
   приложение и добавили раздел — показываем только новое, а не всё заново.
   Ключ читает и пишет только этот модуль, `core/preferences.ts` не трогаем.
6. Приветственный показ монтируется в `src/App.vue` рядом с баннером
   уведомлений (файл A) — один раз, поверх любого экрана, и только для тех, кто
   вошёл.
7. На своих экранах (маршруты, экскурсии) — иконка «?» в шапке, открывающая
   нужный раздел шпаргалки. Чужие экраны не трогаем: сторона B добавит себе
   такие же ссылки по имени роута, когда захочет.

**Проверка.** Первый запуск в чистом профиле браузера; повторный вход — обучение
не всплывает; открытие из профиля работает; «Пропустить» на каждом шаге;
375×667 — текст не выезжает.

## 4. Сторона B — задачи по порядку

### B-1. Уведомления: проверить, дополнить, довести до push (задача 1)

**Что есть сейчас.** `src/features/notifications/` опрашивает
`GET /notifications` раз в 10 секунд и показывает всплывающий баннер поверх
экрана. Экрана со списком нет, push нет (опрос — заглушка вместо FCM).

**Что шлёт бэкенд** (свериться заново: `grep -rn "kind=" backend --include=*.py --exclude-dir=.venv`):

| kind | Кто создаёт | Есть в клиенте? |
| --- | --- | --- |
| `excursion_gathering_started` | search_hq_service, «Начать сбор» | да |
| `excursion_walk_started` | search_hq_service, «Повести группу» | да |
| `trip_cancelled` | search_hq_service, отмена выезда | **нет — баннер не всплывает** |
| `last_stand_nearby` | map_service, новая точка рядом с подпиской | да |
| `achievement` | user_service, выданное достижение | **нет — баннер не всплывает** |

**Шаг 1. Проверить цепочку** (стенд поднят, два аккаунта — краевед и участник):
запись на экскурсию → «Начать сбор» у краеведа → баннер у участника; «Повести
группу» → баннер; отмена выезда → сейчас ничего; точка «Последнего боя» в
радиусе подписки → баннер; выданное достижение → сейчас ничего. Результат
проверки — таблицей в отчёте: пришло / не пришло / где сломалось.

**Шаг 2. Добавить недостающие виды** в `useNotificationWatcher.ts` (`KINDS`):
`trip_cancelled` — ведёт в «Штаб» на карточку выезда, живёт сутки;
`achievement` — ведёт в профиль к значкам, живёт сутки. Подписи и иконки — по
образцу существующих.

**Шаг 3. Центр уведомлений** — новый модуль `src/modules/notifications/`, роут
`notifications`, **без вкладки** в нижней панели:
- список с новыми сверху, непрочитанные выделены, у каждого — переход на экран
  события, «прочитать всё»;
- состояния «загрузка», «ошибка», «пусто», «без аккаунта» — как на остальных
  экранах;
- вход — колокольчик со счётчиком непрочитанных в профиле (`ProfilePage.vue`,
  файл стороны B).

**Шаг 4. Push в APK.** Бэкенд к этому готов: `POST /notifications/devices`
(`platform`, `token`), `DELETE /notifications/devices/{token}`, отправка через
FCM v1 в `user_service/services/fcm_client.py`.
- Плагин `@capacitor/push-notifications` в `package.json` — **это новая
  зависимость, ставить только после подтверждения пользователя**, `npm i`
  выполняет он;
- регистрация токена после входа, снятие — при выходе;
- `android/app/google-services.json` и gradle-плагин Google Services;
- в `user_service` нужны `FCM_PROJECT_ID` и ключ сервисного аккаунта — это
  задача пользователя, в код не лезем;
- **фолбэк обязателен**: нет плагина, нет ключей, обычный браузер — работает
  прежний опрос и баннер, приложение не падает.
- Опрос не выключаем даже при рабочем push: лента уведомлений нужна в любом
  случае.

Если что-то из push упирается в ключи — доделываем всё остальное, а недостающее
пишем отдельным пунктом в отчёт.

### B-2. Роли и заявки (задача 3)

**Что не так сейчас.** Роль у человека одна (`auth_service`, поле `role`), а
заявок можно подать две — на поисковика и на краеведа, в двух очередях
одновременно. Одобрение второй молча перезапишет первую роль: человек нажимал
«хочу краеведом», а потерял права поисковика и не узнал об этом.

**Что делаем** (`src/modules/profile/components/RoleRequestSection.vue`,
`src/modules/profile/data.ts`):
1. Проверить фактическое поведение на стенде: подать две заявки, одобрить обе в
   админке, посмотреть, что стало с ролью. Результат — в отчёт: это же ответ на
   вопрос «бывает ли две роли на самом деле».
2. Пока висит неотвеченная заявка — вторую подать нельзя: форма второй роли
   заблокирована с понятной подписью «Сначала дождитесь ответа по заявке на …».
3. Есть роль сильнее «семьи» и человек подаёт заявку на другую — явное
   предупреждение перед отправкой: какие права уйдут и какие придут, с
   подтверждением. Без сюрпризов после одобрения.
4. Если проверка на шаге 1 покажет, что две роли всё-таки возможны, — выбор
   активной роли в профиле: переключатель, от которого зависит показанный
   интерфейс. Системная развязка `can.*` живёт в `src/core/session/roles.ts`
   (заморожен) — **правку туда не вносим**, описываем в отчёте, сведём после
   мерджа.
5. Заодно проверить, что запись на выезд и на экскурсию не дублируется при
   быстром двойном нажатии (кнопка блокируется на время запроса).

### B-3. Точка штаба отряда на карте (задача 4)

**Что есть.** У отряда в бэкенде уже есть `lat`/`lon` (поля штаба/базы), их
принимают `POST /squads` и `PATCH /squads/{id}`. Клиент их **не шлёт и не
читает**: `squadPlace()` угадывает город по названию региона, и отряд из
незнакомого города на карту потребностей вовсе не попадает.

**Что делаем** (`src/modules/hq/`):
1. `Squad` и `SquadDraft` в `data.ts` — поля `lat`/`lon` (необязательные).
2. В окне организации (`components/NewSquadSheet.vue`) — блок «Где штаб»:
   карта с выбором точки нажатием, кнопка «Поставить по моему местоположению»,
   поиск по адресу с подсказками.
3. Поиск адреса — новый компонент в своей зоне
   (`components/PlacePickerSheet.vue`) на публичном Nominatim
   (`https://nominatim.openstreetmap.org/search?format=jsonv2&countrycodes=ru&limit=5`),
   без ключа, как уже сделано с OSRM в `core/geo/routing.ts`. Обязательно:
   задержка ввода 600 мс (у Nominatim лимит — один запрос в секунду), отмена
   предыдущего запроса, честное «не нашлось» и «сервис не ответил — поставьте
   точку на карте вручную».
4. `squadPlace()` — сначала настоящие координаты, потом прежний фолбэк по
   региону. Точка на «карте потребностей» становится точной.
5. В окне «Набрать волонтёров на выезд» (`components/NewTripSheet.vue`) —
   подсказка, если у отряда штаб не указан, со ссылкой в окно организации.
6. У карт в своём модуле включить проп `expandable` от стороны A (см. §5).

Координаты самого выезда (`VolunteerTrip`) в бэкенде отсутствуют — если
захочется ставить точку ещё и у конкретного выезда, это **пункт в отчёт для
`BACKEND-GAPS.md`** (`lat`/`lon` у выезда), в обход через строку `location` не
лезем.

### B-4. Геймификация детского режима (задача 8)

**Где.** `src/modules/profile/` — своя карточка и, при необходимости, свои
компоненты в `components/`.

**Что делаем.**
1. Включён «Семейный и детский режим» (`usePreferencesStore().familyMode`,
   читаем из ядра, не правим) — профиль показывает игровой блок; выключен —
   всё как сейчас.
2. Звания по реальному прогрессу: «Юный следопыт» → «Разведчик» →
   «Хранитель памяти». Считаем **только из того, что уже отдают сервисы** —

## 5. Договорённости между сторонами

Это то, о чём нельзя договориться постфактум, — фиксируем до старта.

1. **`GeoMap.vue` правит только A.** Появится проп `expandable` (карта
   разворачивается по нажатию). B включает его у себя (`NeedsMap`,
   `LastStandPage` и другие свои карты) — **одной строкой в своём файле**,
   сам компонент не трогает.
2. **Имена роутов фиксированы заранее:** обучалка — `onboarding` (модуль A),
   центр уведомлений — `notifications` (модуль B). Ссылки между сторонами —
   только `router.push({ name: ... })`, импортов из чужих модулей нет.
3. **Ссылка на обучалку в профиле.** Профиль — файл B, поэтому строку «Как
   пользоваться приложением» с переходом на роут `onboarding` добавляет
   **сторона B**. Сторона A профиль не трогает.
4. **Нижняя панель не меняется.** Пять вкладок, порядок и `order` прежние.
   Новые модули — без вкладки.
5. **`src/core/**` не правит никто.** Нужна правка ядра — пишем в свой отчёт.
6. **API общих компонентов только пополняется.** A может переписать
   внутренности `src/ui/*`, но пропсы, слоты и события — не переименовывать и
   не удалять: на них стоят экраны B.
7. **Новые зависимости — только у B и только ради push**, после подтверждения
   пользователя. A в `package.json` не заходит.
8. **`docker-compose.yml` и `.env.example` — зона A** (одна строка радиуса).
9. **Отчёты раздельные:** `HANDOFF-A2.md` и `HANDOFF-B2.md` — общий файл
   конфликтовал бы. Дыры бэкенда пишем туда же, в `BACKEND-GAPS.md` их
   перенесёт пользователь.

## 6. Git: две машины, две ветки

Обе стороны стартуют с одного коммита — `feat/up-mobile` (`ee68c35`).

```bash
git fetch origin && git checkout feat/up-mobile && git pull
git checkout -b feat/up-mobile-a
```

На машине B — то же, но ветка `feat/up-mobile-b`.

- Коммиты: `feat(client/a): …` и `feat(client/b): …` — по одному осмысленному
  коммиту на задачу, а не один общий в конце.
- Перед каждым коммитом — `git status --short`: в списке не должно быть ни
  одного файла вне своей зоны. Попал чужой — откатить
  (`git checkout -- <файл>`).
- Чужую ветку по ходу работы **не мерджим и не ребейзим**.
- Готово — пушим свою ветку, дальше мерджит пользователь: **сначала A** (там
  `GeoMap` и `App.vue`, на которые опирается B), потом B поверх.
- `docker-compose.override.yml` локальный, в git не идёт.

Дев-серверы: у A — `client` на порту 5174 (готовый `.claude/launch.json`), у B
свой конфиг на 5175, чтобы не драться за порт, если обе сессии окажутся на
одной машине.
