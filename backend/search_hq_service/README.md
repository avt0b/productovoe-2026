# search_hq_service

«Поисковый штаб» платформы «Маршруты победы»: отряды, карта их потребностей,
целевые сборы (краудфандинг), календарь выездов **«Выходные с поисковиком»**
(модули 3–4 ТЗ) и **экскурсии краеведов со сбором группы бампом**.

## Запуск

```bash
uv sync
cp .env.example .env          # JWT_SECRET = как в auth_service; DATABASE_URL -> БД search_hq
uv run uvicorn main:app --reload --port 8004
```

Swagger — <http://127.0.0.1:8004/docs>. Тесты: `uv run pytest`.

Демо-штаб Орловщины — три отряда, сборы «Поднять бойца» и «Экипировать
отряд», выезды с чек-листами: `uv run python -m scripts.seed_orel`. Скрипт
идемпотентный, все строки помечены «ДЕМО», даты выездов считаются от дня запуска.

## Архитектура

Стандартный трёхслойный скелет (`api` / `services` / `repositories` + `core`).
Проверки прав вынесены в `services/permissions.py`.

## Сущности

- **Squad** — поисковый отряд (командир = `leader_id` из JWT); опциональные
  `lat`/`lon` (штаб/база) — чтобы потребности отряда можно было нанести на
  карту (модуль 3 ТЗ, «карта потребностей отрядов»).
- **SquadNeed** — потребность: `volunteers` / `funds` / `equipment`,
  `target_amount` + `collected_amount`, статус `open` / `closed`.
- **Donation** — взнос в денежный сбор; при достижении цели сбор
  автоматически закрывается.
- **VolunteerTrip** — выезд с датой, `capacity` и чек-листом новичка.
- **TripRegistration** — запись волонтёра (`registered` / `cancelled`),
  уникальна по `(trip_id, user_id)`, проверяется вместимость.

## Экскурсии и бамп

Краевед заводит экскурсию в точке на карте, люди записываются заранее. На месте
краевед открывает сбор, и каждый участник трясёт свой телефон одновременно с
краеведом. Совпало — участник отмечен как пришедший, а оба телефона получают
ответ одновременно и играют анимацию «Вы вместе!».

### Сценарий

1. **Краевед создаёт экскурсию** — `POST /excursions`: название, точка
   (`lat`/`lon`, по желанию `poi_id` места на слое «ВОВ»), время, число мест.
   Роль `local_historian` / `mentor` / `moderator`.
2. **Люди записываются** — `POST /excursions/{id}/registrations`. Запись
   открыта, пока экскурсия в статусе `scheduled`: пришедших без записи бамп не
   отмечает. Тело запроса необязательно (обычная запись одного человека); школа
   или клуб передаёт `organization_name` и `group_size` — это **коллективная
   заявка** (модуль 5 ТЗ): один представитель держит одну запись на всю группу,
   `capacity` считается по сумме `group_size`, а не по числу строк. Бамп на
   месте всё равно один — от представителя группы, остальных участников
   поимённо система не ведёт (аккаунт у представителя один).
3. **Краевед на месте нажимает «Начать сбор»** — `POST
   /excursions/{id}/gathering/start` со своими координатами. Сервис проверяет,
   что он не дальше `EXCURSION_SITE_RADIUS_M` от точки, и открывает сбор на
   `GATHERING_DURATION_MINUTES`.
4. **Все трясут телефоны** — каждый шлёт `POST /excursions/{id}/bumps` со
   своими координатами и `shaken_ms_ago`.
5. **Сервер сопоставляет встряски.** Участник совпадает с краеведом, если:
   - он записан на эту экскурсию;
   - обе встряски разошлись по времени не больше чем на `BUMP_WINDOW_SECONDS`;
   - оба в радиусе места сбора.

   Совпало — у участника ставится `checked_in_at`.
6. **Краевед видит, сколько пришло,** — `GET /excursions/{id}/gathering` (опрос
   раз в несколько секунд). Закрыть сбор — `POST .../gathering/finish`; по
   истечении срока сбор закрывается сам.

### Почему так устроено

- **Сопоставление по времени и месту, как у приложения Bump.** Координаты
  участника и краеведа между собой не сравниваются: погрешность GPS в телефоне
  5–30 м, «в метре от краеведа» так не проверить. Проверяется, что оба у места
  сбора, а близость подтверждает одновременная встряска и запись на экскурсию.
  Следующий шаг — сравнивать форму движения телефонов; сейчас этого нет.
- **Время встряски считает сервер.** Часы телефонов расходятся на секунды,
  поэтому телефон сообщает только «тряхнули N мс назад», а сервер вычитает это
  из времени приёма.
- **Без WebSocket.** Запрос встряски ждёт встряску другой стороны до
  `BUMP_WAIT_SECONDS` и отвечает, как только она появилась. Краевед и участник
  получают ответ почти одновременно — анимации стартуют вместе. Результат:
  `matched`, `no_pair` (пары не нашлось, трясти ещё раз) или
  `already_checked_in`.
- **Встряски хранятся в памяти** (`services/bump_matcher.py`), живут секунды —
  база и Redis не нужны. Поэтому **сервис должен работать одним процессом**:
  так он и запускается в Dockerfile, без `--workers`. Для нескольких
  экземпляров хранилище встрясок нужно вынести в Redis.
- **Пока запрос ждёт пару, соединение с базой возвращается в пул** — иначе
  группа из двадцати трясущих выбрала бы все соединения.
- **Участник отмечается своим запросом.** Краевед может совпасть сразу с
  несколькими людьми; каждый участник ставит отметку только себе.

Статусы экскурсии: `scheduled` → `gathering` → `finished`, или `cancelled`.

Ошибки бампа приходят с понятным `detail`: `409` — сбор не идёт или человек
далеко от места («Вы в 1900 м от места сбора…»), `403` — не записан.

### Для демо

Проверка «на месте» реальная, поэтому за столом либо создайте экскурсию в той
точке, где сидите, либо поднимите `EXCURSION_SITE_RADIUS_M`. Проверять бамп
нужно на двух телефонах: у краеведа и участника разные аккаунты.

Регистрация на выезд (`POST /trips/{id}/registrations`) шлёт `user_service`
`POST /internal/achievements/award` с кодом `trip_volunteer`; успешный донат
(сразу без шлюза или после подтверждения ЮKassa через `confirm_payment`) —
с кодом `donor` (`services/achievement_client.py`). Недоступность
user_service не мешает записаться/задонатить — ачивка просто не выдастся.

### Статистика профиля: завершённые экскурсии

Когда экскурсия переходит в `finished` (явным `gathering/finish` или само по
себе, первым же обращением после `gathering_ends_at` — см. `_close_if_expired`),
сервис шлёт `user_service` `POST /internal/stats/increment` с `excursions_completed`
(`services/stats_client.py`) — краеведу и каждому участнику, у кого стоит
`checked_in_at` (отметился бампом). Просто записавшихся, но не пришедших на
бамп, не считаем. Переход из `gathering` в `finished` случается ровно один
раз за экскурсию (статус меняется необратимо), так что задвоения счётчика
при повторных обращениях нет. Подробности —
[user_service/README.md](../user_service/README.md#статистика-профиля).

## Рейтинг краеведов

Участник, который отметился бампом, после экскурсии ставит краеведу 1–5
(`POST /excursions/{id}/rating`). Когда экскурсия завершается любым путём,
отметившимся приходит напоминание `rate_excursion` — иначе оценок почти нет.

| Метод | Путь | Доступ |
| --- | --- | --- |
| GET | `/guides/rating` `?period=all\|month&limit&offset` | публично; с токеном своя строка — `is_me` |
| GET | `/guides/{id}/rating` | публично — карточка: место, распределение, отзывы с именами, профиль |
| GET | `/excursions?guide_id=` | публично — ближайшие экскурсии краеведа |

Место — по байесовскому среднему: `(C·M + сумма) / (C + число оценок)`,
`C = GUIDE_RATING_PRIOR_WEIGHT` (5), `M = GUIDE_RATING_PRIOR_MEAN` (3, середина
шкалы). `M` не общее среднее намеренно: когда все ставят 4,8–5, общее среднее
тоже 4,8, и одна пятёрка обгоняла бы двадцать оценок. «За месяц» — скользящие
30 дней. Имена и города — из `user_service` (`/profiles/batch`).

## «Я потерялся»

На прогулке (`walking`) участник группы жмёт «Я потерялся», и тревога уходит
краеведу и членам его семьи, которые сами в этой группе (семья — из
`user_service`, `GET /internal/family/{id}`). Родным дома тревога не приходит:
помочь они не могут. Член семьи или краевед может поднять тревогу и за
другого — «Не вижу …» (`lost_user_id` в теле). Ищущие жмут «Иду», кто-то
жмёт «Нашлись» — поиск закрыт у всех. Координаты — те же позиции группы, что
у прогулки, но без фильтра свежести и с расстоянием до потерявшегося.

| Метод | Путь | Доступ |
| --- | --- | --- |
| POST | `/excursions/{id}/lost` | участник группы или краевед; `201` — новая, `200` — уже открытая |
| GET | `/lost-alerts/active` | авторизованный — тревоги, где его ищут или он ищет |
| GET | `/lost-alerts/{id}` | потерявшийся, ищущие, root |
| POST | `/lost-alerts/{id}/respond` | ищущие — «Иду» |
| POST | `/lost-alerts/{id}/resolve` | потерявшийся, ищущие, root — «Нашлись» |
| POST | `/lost-alerts/{id}/cancel` | потерявшийся, поднявший тревогу, root — ложная тревога |

Пока тревога открыта, краевед не может завершить прогулку или отменить
экскурсию (`409`): иначе телефоны перестанут присылать точки. Тревога живёт
`LOST_ALERT_TTL_MINUTES` (120) и закрывается вместе с прогулкой, вышедшей по
сроку. Полный контракт с JSON и текстами — [docs/lost-and-rating/CONTRACT.md](../../docs/lost-and-rating/CONTRACT.md).

## Чат сбора

И у выезда «Выходные с поисковиком», и у экскурсии есть общий чат для
координации на месте («во сколько встречаемся», «где парковка») —
`GET`/`POST /trips/{id}/messages` и `GET`/`POST /excursions/{id}/messages`.
Оба живут в одной таблице `chat_messages` (`subject_type` = `trip` или
`excursion` + `subject_id`, `services/chat_service.py`) — логика доступа
общая, эндпоинты просто нацелены на разные сущности.

**Доступ проверяется на каждый запрос** (и на чтение, и на отправку), а не
один раз при входе:

- Выезд — командир отряда, `moderator`/root и те, у кого активная
  (`registered`) `TripRegistration`.
- Экскурсия — краевед-ведущий, `moderator`/root и те, у кого активная
  (`registered`) `ExcursionParticipant`.

Отменил запись — потерял доступ к чату этого сбора, включая уже
написанные в нём сообщения (не только к отправке новых). Простое правило
без отдельного состояния «участник чата», согласованное с тем, как уже
работает `gathering_state` у экскурсий.

**Без WebSocket**, как и весь сервис — клиент опрашивает `GET .../messages`
раз в несколько секунд, как и сбор группы на бампе. Автор сообщения — только
`author_id`; человекочитаемое имя фронт достаёт из `user_service`
(`GET /profiles/{id}`) сам, сервис его не хранит и не подтягивает.

Сообщения не привязаны внешним ключом к `volunteer_trips`/`excursions` —
общая таблица на два типа сборов, а удаления сборов в API нет, так что
осиротевших строк на практике не возникает.

**Модерация** (`services/moderation.py`): сообщение с матом отклоняется
(`422`, `detail: "Соблюдайте правила нашего сообщества"`), в чат не
попадает. Встроенный список — только мат; расширить его можно через
`CHAT_BANNED_WORDS` (через запятую) — что банить сверх мата, решает
оператор площадки конфигом, а не зашито в код. Фильтр ловит прямой текст
без обфускации (`п_и_з_д`, замену букв цифрами и т.п. не распознаёт).
