# media_render_worker

Воркер рендера «Живого фото» (модуль 7 ТЗ) — тот самый «главный оставшийся
долг», про который `media_service/README.md` пишет: «реальная генерация
видео... остаётся за внешним воркером». Это и есть внешний воркер.

**Не FastAPI-сервис** — не слушает порт, не входит в таблицу сервисов
`backend/README.md`. Обычный Python-процесс с бесконечным циклом опроса.

## Что делает

Раз в `POLL_INTERVAL_SECONDS` спрашивает у `media_service`, есть ли в
очереди клип (`POST /render/claim`, `queued -> processing`). Если есть:

1. **Yandex SpeechKit** — озвучивает `narration_text` голосом по
   `voice_style` (`clients/speechkit.py`). Текст длиннее
   `MAX_NARRATION_CHARS` (400, ~30 сек речи) обрезается по концу
   предложения — видео оплачивается посекундно.
2. Скачивает фото по `source_photo_url` и вместе с голосом отправляет в
   **Kling AI Avatar 2.0** (`kling-avatar-20`) через шлюз
   [Ranvik](https://api.ranvik.ru/docs/video) (`clients/ranvik.py`) —
   российский агрегатор нейросетей: рубли, без VPN. Получается говорящий
   портрет: боец произносит текст, губы синхронизированы с голосом, моргает,
   двигает головой. Голос уже внутри ролика.
3. Готовый ролик заливает в MinIO (`services/storage.py`, тот же бакет
   `media`, что у `media_service`).
4. Сообщает результат обратно: `POST /render/{id}/ready` с `video_url`, или
   `/failed` с текстом ошибки — тем же токеном, каким брал клип в работу.

## Запуск (локально)

```bash
uv sync
cp .env.example .env    # см. «Что нужно от DevOps» — без ключей просто не будет работать
uv run python main.py
```

Тесты: `uv run pytest` (моки на границе, реальных ключей не требуют).
Линт: `uv run ruff check .`

## Проверка целиком — сначала бесплатно, потом один платный прогон

`scripts/smoke_e2e.py` проходит путь обычного пользователя по живым
сервисам: регистрация → вход → загрузка фото → заявка → ждёт `ready` →
скачивает ролик. Запускается внутри сети compose (сервисы там по именам).

**1. Бесплатно: `RANVIK_DRY_RUN=true`.** Всё настоящее — очередь, SpeechKit,
MinIO, `ready`, — кроме Ranvik: вместо него в MinIO кладётся заглушка
«DRY RUN» (`assets/dry_run.mp4`). Локально ссылки MinIO надо направить на
локальный MinIO (в `.env` — боевой домен):

```powershell
$env:RANVIK_DRY_RUN = "true"; $env:MINIO_PUBLIC_BASE_URL = "http://minio:9000"
docker compose up -d --build postgres nats minio auth_service media_service media_render_worker
docker compose run --rm -v "D:\путь\к\фото.jpg:/in/photo.jpg:ro" -v "${PWD}\smoke:/out" `
    media_render_worker python scripts/smoke_e2e.py /in/photo.jpg /out
```

В выводе — `✓` по шагам и `ready`, в `smoke\` — ролик-заглушка. Логи
воркера: `docker compose logs -f media_render_worker` (там будет
`RANVIK_DRY_RUN: в Ranvik не ходим`).

**2. Один платный прогон.** То же, но без `RANVIK_DRY_RUN` (или `false`) —
пересоздать воркер (`docker compose up -d media_render_worker`) и снова
запустить скрипт. Фраза по умолчанию «Помни меня.» (~1.2 сек) добивается
тишиной до 2.2 сек — минимум Kling Avatar, — это ~13 ₽. Готово примерно за
2 минуты.

**На VPS** — то же самое после деплоя, без переопределения
`MINIO_PUBLIC_BASE_URL`: сначала с `RANVIK_DRY_RUN=true` в `.env`, затем
`false`.

От случайных трат страхует и сам воркер:

- постановка задачи в Ranvik никогда не повторяется (второй запрос — вторая
  оплата), а вот опрос и скачивание готового ролика повторяются при сбоях
  сети: на проверке разовый обрыв CDN Ranvik иначе валил уже оплаченный клип;
- если ролик так и не скачался, в ошибке клипа — id задачи Ranvik и ссылка
  (живёт сутки): ролик можно забрать руками, не генерируя заново;
- голос короче 2 сек добивается тишиной, длиннее 300 — обрезается (иначе
  Ranvik отвечает 400 — это бесплатно, но клип падает);
- текст режется до `MAX_NARRATION_CHARS`, воркер один, автоматических
  повторов клипа нет — «Повторить» жмёт только автор.

## Что нужно от DevOps

Без этих значений в `.env` (или в общем `.env` на VPS — секция
«Живое фото» в корневом `.env.example`) воркер не запустится содержательно:
`RENDER_WORKER_TOKEN` совпадёт с пустым дефолтом только случайно, а без
ключей Yandex и Ranvik любой клип будет улетать сразу в `failed`.

### 1. `RENDER_WORKER_TOKEN`

Не регистрация — просто общий секрет. Сгенерировать любую случайную строку
и прописать **одинаковое значение в двух местах**: `media_render_worker/.env`
и `media_service/.env` (или один раз в корневом `.env` на VPS — обе службы
берут его оттуда через `docker-compose.yml`). Не совпадёт — воркер получит
`403` на каждый вызов `/render/*`.

### 2. Yandex Cloud — `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`

Синтез речи (SpeechKit) — те же голосовые модели, что говорят голосом Алисы.

1. Завести аккаунт на [cloud.yandex.ru](https://cloud.yandex.ru) (понадобится
   привязать карту — есть бесплатный грант, но без карты не пускают).
2. В консоли выбрать/создать **каталог** (folder) — его id и есть
   `YANDEX_FOLDER_ID` (виден в адресной строке консоли или на странице
   каталога).
3. **Identity and Access Management → Сервисные аккаунты → Создать
   сервисный аккаунт.**
4. Аккаунту назначить роль **`ai.speechkit-tts.user`** (именно
   text-to-speech, не распознавание).
5. У этого сервисного аккаунта: вкладка **API-ключи → Создать API-ключ**.
   Значение показывается один раз — сразу в `YANDEX_API_KEY`.

Цена ориентировочно ~1342 ₽ за 1 млн символов (API v1, синтез) — для
монолога на 15–30 сек это доли копейки за клип.

### 3. Ranvik — `RANVIK_API_KEY`

Ключ (`rk_live_…`) — в кабинете [api.ranvik.ru](https://api.ranvik.ru), у
ключа должен быть скоуп `video`. Оплата — рублями с баланса
([цены](https://api.ranvik.ru/pricing)): у Kling Avatar 2.0 — 5.81 ₽ за
секунду голоса на момент выбора, фраза на 5 сек ≈ 29 ₽, потолок при
`MAX_NARRATION_CHARS=400` ≈ 175 ₽. Без денег клип падает с `Ranvik 402: …`.

Необязательные (дефолты в `core/config.py`):

- `RANVIK_MODEL` — `kling-avatar-20`. Другая модель шлюза ждёт другие
  параметры (`clients/ranvik.py` собран под схему Kling Avatar из
  `/v1/models`: `inputs.image` + `inputs.audio`);
- `AVATAR_PROMPT` — необязательная подсказка про мимику (спокойно и тепло
  говорит, естественно моргает, чуть двигает головой). Губы идут за голосом
  и без неё;
- `MAX_NARRATION_CHARS` — 400 (~30 сек речи): длиннее текст обрезается по
  концу предложения, чтобы клип не стоил сотни рублей;
- `RENDER_TIMEOUT_SECONDS` — сколько ждать ролик целиком (900).

## Почему так, а не иначе

- **Ranvik, а не своя модель на GPU или зарубежный API.** Пробовали
  Replicate/SadTalker, свой Kandinsky 5.0 в Cloud.ru ML Inference и LTX:
  зарубежное не оплатить, своё на GPU слишком сложно развернуть. Ranvik —
  российский шлюз, рубли и без VPN.
- **Kling Avatar, а не «оживление» фото + голос за кадром.** На Ranvik
  пробовали P-Video (не моргает ни при каком промпте, в черновике только
  «дышит» масштабом) и Seedance 1.5 Pro (моргает, но наезжает камерой и
  скалится). Kling Avatar единственный моргает, не двигает камеру — и
  вдобавок говорит голосом SpeechKit с липсинком, а не молчит под
  закадровый голос. Дороже (платим за каждую секунду речи), отсюда
  `MAX_NARRATION_CHARS`. Сравнение вариантов обсуждалось в чате при выборе,
  тут — уже решение.
- **SpeechKit отдаёт «голый» LPCM без WAV-заголовка** (`format=lpcm`) — заголовок
  дописывает сам `clients/speechkit.py` модулем `wave`, чтобы модель
  однозначно опознала файл как аудио.
- **Фото и голос уходят данными (data URI), а не ссылками на MinIO.** Ranvik
  не нужен доступ к нашему хранилищу. По схеме модели аудио — только URL,
  но шлюз принимает и data URL (проверено). Фото заранее ужимается до 1280
  по длинной стороне — исходник бывает до 15 МБ.
- **Ролик скачивается сразу.** На CDN Ranvik результат живёт сутки, в MinIO
  он лежит сколько нужно. Ссылку видеомодели отдают в `urls` (списком), хотя
  в документации шлюза написано `url`, — клиент понимает оба.
- **Асинхронно: поставить задачу → опрашивать → забрать mp4.** Генерация
  идёт минуты; держать всё это время одно HTTP-соединение хрупко.
- **Без очереди с повторами.** Как и у остальных внутрисервисных вызовов
  в проекте — ошибка форвардится в `failed`, автор жмёт «Повторить»
  (`POST /clips/{id}/retry` в `media_service`) сам.

## Дальше

- **Если `mark_failed` сам не дойдёт** (сеть отвалилась именно на этом шаге)
  — клип зависает в `processing` навсегда: `retry` в `media_service` работает
  только из `failed`, восстановления для «завис в processing» нет. Известное
  ограничение, не баг.
- **Гонка при `claim_next`, если запустить больше одного воркера.**
  `ClipRepository.oldest_queued()` не блокирует строку (`SELECT ... FOR
  UPDATE`) — два воркера теоретически могут взять один клип и оба его
  обработать (задвоенная оплата генерации, не порча данных: кто вызвал
  `ready`/`failed` последним, тот и победил). Пока рассчитан ровно на один
  инстанс — в `docker-compose.yml` так и заведено, без `replicas`.
- Ретраи с бэк-оффом на сетевые сбои — сейчас одна попытка на клип.
