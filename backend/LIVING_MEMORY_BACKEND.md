# «Живая память» — контракт для бэка (модуль 6 ТЗ)

Фронт (`frontend/web/src/modules/living-memory`) уже полностью реализован
поверх существующего `archive_service` (`ArchiveEntry`, `EntryKind`,
`EntryStatus`, роутер `entries.py`). Ничего из перечисленного ниже не
блокирует текущую работу фронта — это список реальных пробелов между тем,
что просит ТЗ, и тем, что отдаёт бэк сейчас. Оформлено как контракт, чтобы
бэкенд-разработчик мог сразу начать реализацию, не выясняя заново, что
именно нужно фронту.

## Что уже есть и работает (ничего не трогать без причины)

- `POST /entries` — предложить запись (`pending`), любой авторизованный.
- `GET /entries?kind=&q=` — публичная лента (только `verified`).
- `GET /entries/mine` — свои записи любого статуса.
- `GET /entries/moderation?status=` — очередь на проверку, только для
  `searcher/local_historian/mentor/moderator/root` (`EntryService._can_verify`).
- `POST /entries/{id}/verify` / `/reject` — решение по записи.
- `GET /entries/nearby-pending` — витрина для подсказки на карте маршрутов
  (уже подключена на фронте, `RoutesPoiMap.vue`).
- Загрузка фото — `POST /api/media/uploads` (media_service), JPEG/PNG/WebP,
  ≤15 МБ. Общая ручка на всё приложение, не специфична для «Живой памяти».

Фронт полностью функционален на этом контракте: лента, форма публикации
(с фото и текстовой датой), отдельная вкладка модерации с
подтвердить/отклонить прямо в интерфейсе.

## Пробел 1 — аудиовоспоминания (ТЗ: «...фото, аудиовоспоминания...»)

**Сейчас:** `media_service.ALLOWED_CONTENT_TYPES` (`api/routers/uploads.py`)
разрешает только `image/jpeg`, `image/png`, `image/webp`. Загрузить аудио
физически нельзя — фронт эту возможность не может предложить пользователю,
даже если бы очень хотел.

**Нужно:**

1. Расширить `ALLOWED_CONTENT_TYPES` аудиоформатами: как минимум
   `audio/mpeg` (mp3), `audio/ogg`, `audio/wav`. Голосовые воспоминания
   обычно длиннее и тяжелее фото — стоит поднять `MAX_UPLOAD_BYTES` для
   аудио отдельно (например 30 МБ вместо текущих 15 МБ), либо завести
   отдельный лимит по content-type.
2. Проверить, что `storage.upload()` корректно определяет расширение файла
   для аудио (сейчас берётся из `filename`, должно работать без правок,
   но стоит покрыть тестом).

**Не нужно:** отдельный сервис/ручка — один и тот же `POST /uploads` с
расширенным списком типов полностью закрывает вопрос.

## Пробел 2 — одна запись не может нести и фото, и аудио одновременно

**Сейчас:** `ArchiveEntry.media_url` — одно поле, один URL. ТЗ описывает
запись, у которой одновременно может быть фото *и* аудиовоспоминание
(«добавлять... фото, аудиовоспоминания и карточки бойцов»).

**Варианты (от меньшего к большему по объёму изменений):**

- **A (минимум).** Добавить `media_kind: photo | audio | null` рядом с
  существующим `media_url` — фронт по нему решает, рендерить `<img>` или
  `<audio>`. Ограничение: по-прежнему одно вложение на запись.
- **B (рекомендуется).** Отдельное поле `audio_url: str | None` рядом с
  `media_url` (переименовать в `photo_url` для ясности, либо оставить как
  есть и держать в голове, что `media_url` теперь именно «фото»). Позволяет
  прикрепить и фото, и аудио к одной записи, как в ТЗ.
- **C (на будущее, не сейчас).** Отдельная таблица `entry_media` с
  `entry_id, kind, url, created_at` — нужна только если вложений на запись
  когда-нибудь станет больше одного фото + одного аудио. Для текущего ТЗ
  избыточно.

Рекомендация — вариант **B**: минимальная миграция (`ALTER TABLE
archive_entries ADD COLUMN audio_url VARCHAR(500)`), два поля в
`EntryCreate`/`EntryUpdate`/`EntryOut`, фронт уже готов подставить оба —
достаточно передать `photo_url`/`audio_url` вместо одного `media_url` в
`createEntry()` (`frontend/web/src/modules/living-memory/api.js`).

## Пробел 3 — имя автора записи

**Сейчас:** `ArchiveEntry.submitted_by` — это `user_id` (UUID), не имя.
Фронт (`CommunityArchive.vue`) вынужден honestly показывать «Вы» для своих
записей и обезличенное «Участник платформы» для чужих — резолвить
`display_name` по `user_id` не из чего: `GET /profiles/{id}` в
`user_service` существует, но дёргать его по одному на каждую карточку
ленты (N+1) — не вариант для форума с сотнями записей.

**Нужно (любой из вариантов):**

- **A.** Батч-ручка в `user_service`: `GET /profiles/batch?ids=id1,id2,...`
  → `list[ProfileOut]`, публичная, без токена (профиль и так открыт по
  одному ID — см. `GET /profiles/{id}`, «не проверяет владение»). Фронт
  сам матчит по `id` после загрузки ленты.
- **B.** Денормализация: `archive_service` при создании записи спрашивает
  `user_service` (`submitted_by_name: str`) и сохраняет сразу в
  `ArchiveEntry` — эта информация статична (человек редко меняет имя за
  время жизни записи), можно не синхронизировать при переименовании.

Рекомендация — вариант **A**: чище архитектурно (не плодит меж-сервисную
запись при каждом POST), переиспользуется другими местами, где тоже нужен
список имён по ID (например будущая витрина авторов в модерации).

## Пробел 4 — роль «музейщика» / «учителя истории» отдельно от прочих

ТЗ: «...краеведов, учителей истории, сотрудников музеев и поисковиков с
правами верификации...». Сейчас `Role` (`auth_service/core/models/user.py`)
не различает учителя истории/музейщика отдельно от `local_historian` —
верификация уже доступна `searcher/local_historian/mentor/moderator`
(`VERIFIER_ROLES`), т.е. де-факто всем ролям, кроме `family`. Если четыре
существующие роли покрывают смысл ТЗ (историк-учитель регистрируется как
`mentor` или `local_historian`) — новых ролей не требуется, править
`RoleUpdate`/`Role` не нужно. Если продукту принципиально различать
«музейщика» как отдельную сущность (например для отдельной статистики) —
это отдельное решение, не блокирующее текущий контракт.

## Итог: что реально стоит сделать бэку, по приоритету

1. **Пробел 1** (аудио в `media_service`) — маленькая правка, разблокирует
   реальную функцию из ТЗ, которой сейчас физически нет.
2. **Пробел 3, вариант A** (батч-ручка имён) — без неё лента честно
   обезличена, хотя технически работает.
3. **Пробел 2, вариант B** (`audio_url` в `ArchiveEntry`) — зависит от
   пробела 1 (аудио сначала нужно куда-то загрузить).
4. Пробел 4 — только если продукт явно попросит различать роли отдельно.
