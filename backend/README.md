# Backend — «Маршруты победы»

Микросервисная архитектура. Каждый сервис — независимый проект на **FastAPI**
со своим `pyproject.toml`, своим окружением и своей БД. Управление зависимостями —
**[uv](https://docs.astral.sh/uv/)**.

## Служебная плоскость `/internal/*`

У каждого сервиса есть закрытый префикс `/internal/*` — по нему ходит только
`admin_service`. Аутентификация там не пользовательская: общий секрет в
заголовке `X-Internal-Key` (`INTERNAL_API_KEY`, одинаковый во всех `.env`) плюс
`X-Actor-Id` с id администратора — в журнал аудита `admin_service` он попадает
всегда. В данные сервиса-владельца актор реально оседает не везде: например,
`archive_service` пишет его в `verified_by` при verify/reject через internal,
а вот `user_service` (`Profile`) и `map_service` (`PointOfInterest`,
`LastStandPoint`) принимают `X-Actor-Id`, но не хранят его ни в одном поле —
единственная запись о том, кто именно выполнил такую мутацию, остаётся в
аудит-логе `admin_service`, а не в самих данных.

```
Vue-админка ──JWT админки──► admin_service ──X-Internal-Key──► /internal/* сервисов
```

Каждый сервис отдаёт `GET /internal/stats` (сводка для плиток дашборда),
`auth` / `map` / `archive` — ещё и `GET /internal/stats/timeseries` для графика.
Остальные ручки — списки с фильтрами и действия модерации.

**Наружу `/internal/*` публиковать нельзя** — закрывается на reverse proxy.

## Запуск сервиса

```bash
cd backend/<service>
uv sync
cp .env.example .env          # поправить DATABASE_URL / JWT_SECRET при необходимости
uv run uvicorn main:app --reload --port <порт из таблицы>
```

Swagger: `http://127.0.0.1:<порт>/docs`. Тесты: `uv run pytest` (sqlite во
временном файле, Postgres не нужен). Линт: `uv run ruff check .`.

## Локальные БД (без Docker)

PostgreSQL 18 на `127.0.0.1:5432`, роль `marshruty` / пароль `marshruty`,
отдельная БД под каждый сервис: `auth`, `users`, `map`, `search_hq`, `archive`,
`routes`, `media`, `admin`.
Схема создаётся на старте (`core.db.init_db` → `create_all`); alembic —
задел на потом. `.env` каждого сервиса в git не попадает.

**В Docker** базы создаёт `docker/postgres/init/01-create-databases.sql`:
Postgres выполняет его один раз, при первом запуске с пустым томом `pg_data`.
Сервис со своей новой базой — допишите её в этот файл и пересоздайте том
(`docker compose down -v`) или создайте базу руками.

## Структура сервиса (3 слоя)

```
<service>/
├── api/            # HTTP: роутеры + pydantic-схемы валидации + deps
├── services/       # бизнес-логика, оркестрация, транзакции
├── repositories/   # доступ к БД (только SQL)
├── core/           # config, db (инициализация), security, exceptions, models/
├── main.py         # сборка FastAPI
└── tests/
```

Роутер вызывает сервис → сервис вызывает репозитории и владеет `commit` →
репозиторий трогает только БД.

## Аутентификация (кратко)

`auth_service` подписывает JWT по **HS256** общим секретом `JWT_SECRET`;
остальные сервисы проверяют токен тем же секретом локально, без похода в auth
на каждый запрос. Из токена берутся `sub`, `role` (Enum) и `is_root` (флаг
админки). Прод-апгрейд — RS256. Подробности —
[auth_service/README.md](./auth_service/README.md).

**У админки контур отдельный.** `admin_service` держит свою таблицу
администраторов, свой секрет (`ADMIN_JWT_SECRET`) и свой issuer, а вход требует
TOTP. Пользовательский токен в админке не работает, токен админки — в публичных
сервисах: утечка одного контура не открывает второй. Подробности —
[admin_service/README.md](./admin_service/README.md).

> Домены вида `*.local` в email использовать нельзя: `email-validator`
> считает их зарезервированными и отвергает на входе (`422`). В `.env.example`
> поэтому стоит `marshruty.ru`.
